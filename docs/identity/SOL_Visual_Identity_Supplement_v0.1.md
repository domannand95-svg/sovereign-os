# SOL Visual Identity Supplement v0.1

## 1. Core Principles of the Visual System

The SOL visual language is derived directly from its architectural invariants and the alchemical-solar identity canon. It rejects corporate tech aesthetics and generic sci-fi tropes in favor of monumental, precise, and structurally rigorous design.

* **Zero Metaphor Leakage:** Visual motifs represent architectural facts (boundaries, state references, proofs, gates). They must never invent unallocated operational semantics or obscure technical reality.
* **Restraint as Authority:** High-density ornamentation signals a lack of control. SOL assets utilize sparse, razor-thin geometry, high contrast, and disciplined placement to convey mathematical and operational certainty.
* **The Three-Layer Firewall:**
  * **Layer A (Normative):** Plain diagrams, exact monospace text, no decorative symbols.
  * **Layer B (Architectural Identity):** Concept art, architectural essays, and structural overviews using restrained solar/alchemical framing.
  * **Layer C (Brand & UI):** The core seal, palettes, line systems, and dashboard components.

## 2. Palette & Materiality

The color space simulates the vacuum of space, celestial illumination, and the precision of scientific copperplate engraving.

* **The Dark Field (Vacuum / The Base):**  
  `#0A0A0C` (Deep, light-absorbing black-gray) — Used as the universal background. Represents the fail-closed perimeter where unverified operations cannot exist.

* **Titanium Ash (Structure):**  
  `#8A8D93` (Muted silver-gray) — Used for unexecuted gates, metadata, wireframes, and structural linework.

* **Solar Core (Proof / Admission):**  
  `#FFB020` (Incandescent amber/gold) — Used **strictly** for successfully admitted proofs, active core states, and authoritative state pointers. Never used for general UI decoration.

* **Verification Ivory (Text / Light):**  
  `#F4F4F6` (Warm white) — Used for primary typography and high-contrast data readouts.

## 3. Permitted vs. Forbidden Symbolism

| Permitted Symbolism | Forbidden Symbolism |
| --- | --- |
| **Concentric geometry & orbital rings:** Representing deterministic gate sequences and bounded state references. | **Mystical/Occult iconography:** Tarot symbols, runes, esoteric astrology, or pseudo-religious sigils. |

| **Solar discs & eclipse boundaries:** Minimalist circles, focal points, and razor-thin horizon lines. | **Organic/Biological clutter:** Organic foliage, fluid blobs, hands, or anthropomorphic branding. |

## 4. Key Graphic Motifs & Component Architecture

### 4.1 The Core Seal (Emblem)

The foundational mark for documentation covers, dashboard headers, and architectural splashes:

* **Geometry:** A thin, precise outer circle representing the absolute admission boundary.
* **Center:** A single focal point or micro-ring representing the cryptographic `Caid` and authoritative state.
* **Horizon:** A clean horizontal threshold line bisecting or grounding the seal, representing the Eclipse Boundary.
* **Subdivision:** Six primary bands representing Gates 1–6, with Gate 3 visibly bifurcated into 3A and 3B. The geometry must preserve the actual admission ordering rather than implying six undifferentiated stages.

### 4.2 Gate Architecture Diagrams

Replacing generic boxes and arrows with architectural thresholds:

* Concentric rings or sequential chamber gates where data passes through progressive, irreversible verification barriers.
* Visual narrowing of input channels: unverified data is rejected at the perimeter (calcination), while compliant payloads pass cleanly to the core.
* Gate 3 must preserve its explicit 3A / 3B split wherever the full Capability V1 admission path is shown.

### 4.3 Raw-to-Admitted Transformation Panels (UI / Documentation)

A standard layout block for displaying state change:

* **Left (Prima Materia):** Raw artifact, unstable input, monospaced block representation.
* **Middle (The Alchemical Alembic):** The Gate 1–6 sequence, validation checks, and state binding.
* **Right (The Admitted Grant):** The successfully admitted Capability V1 grant, cryptographically and contextually bound to its declared references and governing-policy authorization, marked with a restrained Solar Core amber highlight (`#FFB020`).

## 5. Canon Axioms for Design Copy

When identity copy, dashboard empty states, or documentation intros require contextual phrasing, use only canon-approved axioms:

* *Probabilistic intelligence; deterministic authority.*
* *Intelligence may explore beyond the boundary. Effects may not.*
* *The core governs; the ecosystem participates.*
* *Authority must be resolved against its authoritative context before it can be exercised.*
* *What cannot be verified does not cross the boundary.*
* *Unverifiable authority is extinguished at the perimeter.*
* *Raw artifacts do not inherit authority.*
* *Admission is purification through proof, context, and authorization.*

---

## 6. Usage Boundary

This supplement governs non-normative visual and identity work only.

It does not define:

* technical authorization semantics;
* Capability V1 schema behavior;
* policy evaluation rules;
* registry state transitions;
* runtime permissions;
* admission outcomes; or
* implementation requirements.

Where visual symbolism conflicts with normative specifications or merged architecture decisions, the normative architecture governs.

The SOL Identity Canon remains the parent identity document. This supplement defines how that identity may be represented visually without creating new technical meaning.
