# Sovereign OS v0.1 Acceptance Contract

## Definition

Sovereign OS v0.1 is a bootable single-node lifecycle that restores authoritative state, evaluates one directive through a minimal fail-closed policy boundary, persists the accepted transition, and deterministically reconstructs the same state after restart.

## Acceptance Criteria

1. **Boot and restore.** Given an empty, snapshot-backed, or ledger-only storage root, engine startup MUST invoke the ledger restoration coordinator and produce the expected final LSN and state root. This is verified by the boot_restart integration test.
2. **Directive admission.** Given one supported kernel directive, the engine MUST decode it into the canonical ledger/domain representation or reject it without mutating live state. This is verified by accepted- and malformed-directive cases.
3. **Policy enforcement.** Before state mutation or acknowledgement, a minimal deterministic policy evaluator MUST return an explicit allow or deny decision. Denial and evaluator failure MUST leave both ledger tail and live state unchanged.
4. **Durable persistence.** An allowed directive MUST be appended and flushed before success is acknowledged. A crash before acknowledgement MUST expose either the previous committed state or the fully committed directive, never a partial transition.
5. **Restart reconstruction.** After volatile state is discarded and the engine is restarted, restoration MUST reproduce the pre-crash final LSN and byte-identical state root without manual intervention.
6. **Snapshot fallback.** If the newest snapshot is malformed, checksum-invalid, root-invalid, or beyond the ledger tail, startup MUST reject that candidate and deterministically select an older valid snapshot or full genesis replay.
7. **Lifecycle equivalence.** Snapshot-plus-delta restoration and full genesis replay over the same ledger MUST produce equal final LSNs and state roots.

## Sprint Exit Command

The v0.1 milestone is complete only when the repository provides and passes:

    cargo test --workspace --test boot_restart

The test MUST exercise boot, directive admission, policy evaluation, persistence, process-state discard, restart, and deterministic reconstruction.

## Implemented Integration Evidence

- Engine startup invokes `initialize_from_snapshot_or_replay`.
- `RegistryGraph` is rebuilt as a deterministic full-ledger projection and must reach the authoritative restoration LSN.
- Directive admission uses an explicit deterministic allow/deny policy contract.
- Accepted directives are preflighted, appended, flushed, and only then published to live state.
- Restart-safe append initialization resumes from the validated ledger tail.
- The public `boot_restart` test exercises two persisted directives across two volatile-state restarts.

## Crash-Atomicity Evidence

- Records are written and synchronized under a non-canonical pending name before atomic publication.
- The ledger directory is synchronized before append acknowledgement.
- A subprocess crash at pending-sync, canonical-publication, and directory-durable boundaries is exercised by `boot_restart`.
- Restart exposes the previous state before publication and the complete directive after publication; no partial transition is visible.

## Out of Scope

- Multi-node consensus or replication
- Network peer discovery
- User interface
- Performance optimization beyond correctness bounds
- General-purpose policy language
- Production observability and operational hardening
